## Architecture and alternatives

Selected: a small **account-specific cash subledger and reconciliation layer in the existing FastAPI/PostgreSQL backend**, linked to existing proof evidence, collection allocation, release/payroll/expense workflows and protected General Ledger (GL). Web, Android and Desktop consume the same server results. It is not a replacement accounting engine, wallet API, payments gateway or second loan allocator.

Rejected alternatives: (a) adding a GCash note to a Collector cash entry cannot establish money destination or correct custody; (b) entering a separate spreadsheet total in every client produces competing balances; (c) simulating provider success or scraping GCash bypasses the intended verification boundary. No direct money-sending integration, SMS listener, OCR approval, automatic statement parser or external matching service is required for this version. Manual statement-row entry/matching and private history attachments are sufficient. Account identity supports separate wallets/banks, but start with only the accounts the owner actually supplies.

Current source facts to preserve:
- `client_payment_proof_repository.py` and SQL0127 are append-only, evidence-only; `reviewed` is not an official payment. API **and repository** currently require Client upload / Management review. Staff submission/delegation needs explicit server changes, not a button or a blanket Management role.
- `collection_api.py` uses `CollectionSubmissionService`, `PostgresCollectionExecutor` and `ConcurrentReceiptSafeCollectionPostingBridge`; allocation/custody/receipt writes are protected. The base `collection_posting.py` describes transaction amount as real custody cash.
- `remittance_repository.py:_eligible_items` currently selects by recorder/date/unlocked/nonvoid, without an owner-wallet funding discriminator. Audit all consumers and SQL triggers, not only this query.
- Existing `cash-disbursement.js` prepares a draft, does not send money, and has broad1010/1030 account choices. A ledger account code is not a unique real wallet.
- Existing Regular journal preview uses `cash_collector_custody`. A manually verified owner-wallet receipt must never enter that accounting path as fabricated Collector cash.
- `gcash_gateway.py` and `client_gcash_api.py` intentionally block live checkout without provider-specific settlement verification. Manual verification must not set that provider capability true.

## C1 — Account identity, scope and access

Create a bounded `treasury` schema (or reuse an exact equivalent found at execution), with real-account IDs distinct from GL account codes. Each account records `ledger_context_id`, `kind` (`physical_cash`, `gcash`, `bank`, `transit`), PHP currency, alias, legal holder/owner classification, actual custodian, masked identifier, restricted verification details, and active/version status. Do not create both Owner Cash and Office Cash for the same pile of notes. Physical cash is tracked by actual location/custodian; responsibility while in transit is separate from location.

Contexts are explicitly `owner_operations`, `corporate_legal`, or `synthetic`. Synthetic environments are isolated. Existing records are not automatically corporate or owner records: bind source IDs to a reviewed context, refusing conflicting context links. No mass reclassification of loans or old journals. Owner-ledger movements must not flow into future corporate legal books or dashboards as legal income/capital. A corporate GL mapping stays blocked until separately configured and authorized.

Proposed permissions: `treasury.account.manage`, `treasury.view`, `treasury.proof.submit.assigned`, `treasury.proof.review`, `treasury.receipt.verify`, `treasury.payment.apply`, `treasury.disbursement.record`, `treasury.transfer.record`, `treasury.reconcile`, `treasury.adjust`. Staff permissions additionally require an explicit per-account scope. Permissions do not bypass existing loan/release/payroll approval rules. No mass grant to Employee/Collector or role upgrade. Use the established owner identity mechanism; if unconfigured, privileged setup is unavailable rather than inferred from a name or first user.

Client can submit/view own claims under authenticated own-borrower access. Assigned/otherwise explicitly authorized Collector can submit on behalf and see only the relevant claim/status. Recheck assignment, device, actor and object authority server-side, including file reads and retries. Management membership alone does not expose another person's full personal wallet. Owner verification is the default; delegated receipt verification requires specific account authority and legitimate recipient-side evidence. Proof review and final money verification/application are separate capabilities.

Provide server-controlled payment instructions for a designated receiving wallet: intended recipient/number/QR as needed to pay, with no balance/history exposed. Changes are owner-authorized and versioned; old claims retain the recipient version they referred to. Never collect or store MPIN, OTP, wallet password or provider secrets. Full-wallet statements/personal movements are owner/restricted-treasury only; client/collector exports receive their own proof/receipt projections, never the underlying private statement.

## C2 — One actual movement, multiple linked purposes

Use these bounded entities: accounts/access; opening positions; structured proof claims/versions/evidence links; external event identity and immutable movement lines; receipt applications/source links; transfer correlation; reconciliation sessions/observations/matches; durable command outcomes. Reuse existing private file storage and `core.audit_logs`. Keep event lines distinct from lightweight current-state/version projections; no general event bus or CQRS framework.

Each actual event has immutable ID, account/provider/canonical reference (where available), direction, exact principal/fee/net components when evidenced, occurred/observed/verified/recorded times, actor/device, evidence references and classification. `funds_account_id`, `recorded_by_user_id`, `reported_by_user_id`, `verified_by_user_id`, and `assigned_collector_user_id` are different facts. An official collection transaction links to its receipt/application and authoritative funding destination, not a guessed value from a note.

Only verified actual account movement affects the expected cash balance. Pending proof, planned transfer, approval, allocation preview, expense draft and GL posting do not create additional cash. Unknown observed credits/debits may be recorded once as `verified_unclassified` with an exception; lacking business approval must not hide an actual debit. Such an observation does not authorize that expense/release or credit a loan.

Money uses exact decimal text on every API and Decimal/NUMERIC in the backend, PHP only initially. Reuse existing approved amount validators/limits for each protected source. Publish exact limits in the implemented contract; do not loosen source limits or round extra precision silently. Receipt amounts are positive with a separate direction; explicit zero is allowed for opening/balance observations, not a payment. Unknown is null/unavailable, never zero. Totals come from complete authorized server queries, not currently displayed pages.

External identity is unique within real account/provider/transaction namespace. Keep original and conservatively normalized reference (trim only unless a verified provider rule says more; preserve leading zeros). A transaction's fee and principal may be components of one parent event; import/matching must not duplicate both a net row and its gross/fee components. Incoming/outgoing/reversal identity must be explicit, not fabricated reference suffixes. If reference is missing, retain an owner-only unresolved observation with stable internal identity and evidence; do not invent a provider reference or permit unattended loan credit. Any manual exception must have independent distinguishing evidence and an auditable reason.

All commands use stable request UUID, action, actor/device, target, canonical payload hash and expected versions. Replay after timeout returns the same durable result after current authorization checks; changed payload with the same key conflicts. Global source/reference uniqueness also prevents duplicates submitted from another device or role. Use transaction locks in a documented consistent order and atomic business-write/audit/result persistence. Never use a browser checkbox or image hash as the sole duplicate/payment authority.

## C3 — Evidenced opening position, not fictional capital

Opening setup collects account alias/custodian, actual observed balance, common Asia/Manila cutoff, evidence/counter, known personal/third-party amounts and in-transit/unapplied items. Capture UTC instants and display Manila time; date-only source fields remain calendar dates. Count sequentially only with a documented bridge of intervening movements. Receivables, unreceived promises, undisbursed approvals and the same cash under another holder are not additional cash.

Allow draft setup without amounts; activation needs actual supplied values and explicit owner confirmation. Determine whether real existing movements already cover the starting point. Choose either a verified opening-at-cutoff with subsequent movements, or an existing reconstructed history anchored earlier; never add both. State coverage starts at the chosen cutoff, not that earlier history has been reconciled.

Formal rule for active opening `B0` at cutoff `t0`: expected account balance at `t >= t0` is `B0 + sum(verified signed movement lines with t0 < effective_at <= t)` for that account/context. `effective_at` is the verified cash-movement time, not upload/review/GL posting time. Unknown event timing cannot silently be assigned across the cutoff. Events at/before cutoff can be retained as `included_in_opening` historical anchors, with no additional balance delta.

A pre-cutoff GCash receipt allocated to a loan later is already in B0: keep its positive receipt/application capacity, but no second wallet inflow. Collector cash counted at cutoff can be linked to preexisting unremitted collections without adding them again. A transfer straddling cutoff needs opening transit plus destination receipt bridging, not double-held cash.

Opening-position revisions are append-only, uniquely active per account/context, with impact preview and explicit reason. Supersession never turns a corrected starting count into income or an unexplained plug. Preserve closed reconciliation revisions. Initial funds are not automatically paid-up capital, equity, income or retained earnings, and this setup is not a full opening balance sheet. Future corporate opening/funding requires separate evidence and legal/accounting authority. Actual balances and wallet details must not be committed to this public repository, PR, CI logs or fixtures.

## C4 — Client and Collector proof in one verification workflow

Keep Client direct upload and add scoped Collector-assisted upload using the same private evidence/version infrastructure. Structured claim fields: borrower/loan or same-borrower loan intentions, selected receiving-account/version, claimed amount/reference/time, sender note, submitter identity and exact proof version. A relative may pay: sender identity need not equal borrower phone, but the received transaction and intended allocation must be verified.

Existing proof metadata stays evidence-only and compatible. Add linked claim/receipt state; never redefine old `reviewed` as `paid`. Clients cannot supply verifier, official receipt ID, bank balance or settlement status. Collector must not impersonate Client. Staff may request correction/reject evidence with reason, but may not certify incoming money without the appropriate receipt authority.

Customer-facing states: **Pending verification / Needs correction / Rejected / Received — awaiting recording / Recorded**, with **Partly applied — amount remaining** if relevant and controlled reversal history. Correction versions retain originals. Duplicate reports link to the same verified external receipt under authorized review; a bogus first claim cannot reserve someone else's transfer. Conflicting borrower claims remain blocked for investigation, with no disclosure of another borrower's identity.

Pending proof does not alter wallet cash, loan balance, PASS, maturity or penalties. Show a pending follow-up flag so staff do not mistake it for no communication; do not automatically mark Paid/Unable or freeze the schedule indefinitely. Only the protected allocator changes official obligations. Denied reupload or a stale file version invalidates the confirmation; routine local refresh must retain unrelated drafts/files without extending authorization.

## C5 — Verify receipt, then apply through protected loan rules

Recipient verification requires checking the actual receiving account transaction and recording exact reference, recipient, amount, timestamp and retained recipient-side evidence/attestation. Label it **Manually verified**, never API verified. Screenshot content from the sender, OCR, notification appearance and a provider redirect are not receipt authority. Reuse validated private file limits and integrity/version checks.

Verification commits the external receipt/movement exactly once. Application is a separately linked transaction against the existing Regular/7x7/combined/covered-date machinery. A single UI **Confirm receipt and record payment** may orchestrate verify then apply with distinct stable phase IDs; it must truthfully return Received—awaiting recording if allocation cannot complete. Crash between phases must recover verified receipt state, not lose real cash or create it again.

Proposed application preview returns same-borrower allowed loan IDs, versions, exact amounts/covered dates/intents, remaining receipt capacity and a server digest. Apply locks and revalidates that snapshot, account/context, receipt capacity and action permissions, then atomically stores official transaction(s), immutable allocation evidence, funding link, audit and replay result. A two-loan Regular+7x7 application succeeds together or neither succeeds. No internally forged Collector session, made-up device sequence or HTTP call to self that creates a second database transaction. Extract a narrowly reusable transaction-level seam if necessary, with regression proof; do not fork the allocator.

Receipt capacity is exhausted by applied and actually refunded amounts; an approved excess allocation/refund is not silently assumed. Same-day mixed cash+GCash and later cash while proof is pending revalidate outstanding obligations. A preview can be stale after another payment. Leave excess as received/unapplied with an explicit authorized resolution, not forced principal reduction or phantom refund. Never count this unapplied balance again on top of wallet funds.

Keep actual received, claim submitted, verified, applied/recorded and accounting dates separately. Do not backdate by trusting a typed photo date or erase penalties. Late payments need the existing authorized schedule/correction/closed-period rules; when no safe historical application exists, preserve the verified receipt and return the exact blocker. Test this case; no silent fallback to today's installment.

## C6 — Cash custody, remittance and accounting stay truthful

Establish an authoritative funding-source link visible **inside the same posting transaction before source/audit/accounting classification runs**. Destination values include Collector physical cash, owner/office wallet and bank; source metadata is populated only by trusted receipt/cash workflows. Legacy cash paths keep their existing default behavior. Never insert a fake cash collection and patch it to GCash afterward.

Inventory every reader/writer using recorder identity or collection amount as custody: ordinary/cross-area remittance, cash-status cards, refunds, direct Management payments, route receipts, dashboards, shortages, cash control, GL preview/post/reversal and database triggers. Owner-wallet receipts must be excluded from Collector cash-to-remit and Collector custody accounting at the server. Preserve collector assistance/route attribution separately; receiving money in the owner's wallet is not a remittance or collector shortage.

Synthetic no-other-movement example: Collector cash3000 + verified/applied owner-GCash1200 + pending claims400 = official loan payments4200, Collector cash due3000, pending400 excluded. This example is not the owner's actual funds and is not a new commission rule.

GL posting remains explicit Management review with `automatic_source_posting=false`. Reuse protected source keys/periods/accounts/independent approvals/reversals; an event can affect operational cash before a journal posts, and later posting has zero additional subledger movement. Map account/legal ownership and source context, not simply1030 for every owner wallet. Unmapped/personal/pre-registration sources must not be proposed as legal Collector custody cash; expose a posting blocker instead of wrong lines. Prove both Regular and7x7 paths and retained legacy cash behavior. No tax, EIR or income formula is introduced.

## C7 — Disbursements and all other account movements

Track actual loan releases/renewals, expenses, salary/advance payouts, refunds, cash-in/out, deposits, owner contributions/withdrawals, fees and personal transactions when the full wallet is in scope. Every verified debit/credit is visible even before its purpose is resolved. This register records what happened; it never sends money or grants release authority.

Approvals/drafts and actual execution are different. Select a specific funding account on the relevant existing workflow. Require the exact authorized source/version/payee and actual outgoing transaction evidence to mark a business disbursement paid. Keep existing borrower acceptance/signing/first-loan office processing, payee acknowledgment, cash-release, payroll and owner-only controls. Do not label a GCash transfer as physical-cash receipt or let a generic expense action release a loan. If an existing source cannot yet represent wallet execution safely, add that typed adapter with tests or retain a visible blocked linking state; never use a cash-only endpoint with fictional evidence.

Once a debit is verified, reduce expected wallet balance even if destination confirmation is pending. Show **Debited — destination not confirmed** and retain reconciliation, with no automatic resend. An approval reserves cash only where an existing explicit reservation exists; do not invent a lending-capacity engine. Whole-wallet balance is not all spendable business cash. Unknown personal/third-party/committed portions make unrestricted available-funds claims unavailable.

Expense/payment record, imported statement row and posted journal referring to one outflow link to one movement, not three. Where fees are separately evidenced, show principal, fee and total debit without charging the borrower automatically. A net-only provider record cannot justify invented gross/fee amounts. Partial/multiple payouts consume the approved amount only once per verified source; concurrent over-application conflicts. Cancellation after actual debit does not remove the debit.

## C8 — Transfers, refunds and controlled corrections

A transfer between tracked accounts has one correlation and linked source/destination legs, each verified at its real time. Source cash leaves once, transit is tracked, destination balance rises only on evidence/required custody acceptance. Preserve sender accountability until existing receiver acceptance while locating the funds once; aggregate physical cash and transit must not double count responsibility records. Cross-wallet matching may involve different provider references; never merge by equal amount alone.

An own-bank to own-GCash transfer is neither borrower collection nor income/expense apart from evidenced fees. Confirmed sides reconcile individually at each cutoff; unresolved side remains transit. Transfers to untracked third parties have one tracked leg and proper purpose, not a invented internal destination.

Differentiate (1) mistaken subledger entry correction, (2) loan application void/reallocation, (3) actual provider refund/reversal, and (4) GL reversal. These have linked but different effects. Reallocating a genuine receipt between loans does not change wallet balance. A provider refund has its own actual debit. A loan void without refund leaves money unapplied or refund due. False receipt verification reverses only its erroneous operational observation, with investigation and protected unwind of downstream application/GL; no history deletion.

Corrections require reasons, current versions, affected-source preview and explicit restricted authorization; immutable originals persist. Do not automatically release an external reference for reuse after a reversal. A future resubmission is linked and independently verified. Never guess historical GCash records from text and bulk reclassify them.

## C9 — Transaction and balance reconciliation

Use owner-accessible manual statement-row capture or private original history attachment plus manual row entry; no provider-specific CSV parser is assumed. An observation is not an approved loan payment. Match observed transaction to one event/component set using account/reference/direction/exact amount/time and documented exceptions, not just screenshot appearance or same amount. Include all real wallet movements, including private personal transactions; hide them from ordinary staff.

Reconciliation stores account/context, cutoff/opening reference, movement watermark/version, actual balance, expected balance, signed difference `actual - expected`, evidence, coverage interval, matches, unresolved items and reviewer. Pages use server totals plus deterministic pagination, never totals of loaded rows. Matching a statement row to an already recorded movement creates no additional cash. Rows/fees shown in alternate net/gross representations must not double count.

Status distinguishes **Draft / In progress / Balanced with unresolved items / Reconciled / Superseded**. Zero difference alone is not Reconciled: all required statement rows and ledger entries in the declared coverage need valid matches, no unexplained difference or unmatched final movement. Pending-unverified borrower claims and externally incomplete transfers remain separately visible; a statement genuinely showing a debit can be reconciled at that account while its destination/loan purpose remains unresolved. State clearly that wallet reconciliation does not close the loan/GL exception.

Save/close locks and verifies expected movement/account/opening versions. Concurrent/backdated entries require refresh. New late evidence affecting a closed interval must retain the original closed result and create a reviewed superseding reconciliation; later dependent closes must be flagged for re-review. No balance-edit box, forced plug, automatic expense for differences or deletion of unmatched rows. Equal balance with two offsetting missing entries is a required failing test.

Every balance is labeled by account, context, cutoff, coverage and last verified timestamp. Missing initial count means **Opening position not supplied**, not0. Failed reads mean Unavailable, not empty/reconciled. Private export includes the reconciliation, matching ledger and exceptions with source IDs; use existing authorized export/file controls. Do not export personal wallet details to Clients/Collectors.

## C10 — User interfaces and source parity

Management/owner: **Cash & GCash Control** under existing financial tools, with Accounts, Verify payments, Money in/out, Transfers, Reconcile and History/Exceptions. Show expected, last observed actual, variance, unapplied receipts and unconfirmed debits with timestamps; do not add these subsets to wallet balance a second time. Employee sees only delegated queues/actions and account projections. Avoid exposing a personal whole-wallet balance simply because staff can review a single proof.

Collector: preserve normal cash Pay/Unable and one-tap behavior; add **Report GCash payment** for the exact authorized borrower, photo/reference form, duplicate-safe status and official receipt after application. Separate cash-to-remit, applied owner-GCash and pending claims. Do not infer a GCASH badge from note text. Client: own **Submit GCash proof**, correction/history/status, same-loan application/receipt, and prescribed receiving instructions. Both entry points share the receipt/claim service, not rival encoders.

Web and Android keep existing branding/navigation/privacy rules. Local saves refresh affected regions only, preserving unrelated text/selected file and pending command state. Permission/session/device changes dispose private views; read retry cannot unlock an uncertain financial command. Narrow layouts, long reference/money, keyboard, meaningful focus and accessible labels are mandatory. Notifications use verified own-record IDs and disclose no unrelated wallet history.

Desktop uses the same authenticated backend endpoints, not direct SQL or a new local allocator. Reconcile its actual runtime Cash Control entry point before wiring; an archived modularization proposal is not proof those proposed files exist. Existing forecasting/planning displays remain distinct from actual account balances. Receipt, collection, remittance and cash reports project the same source classification and cutoffs. Preserve existing three-per-page/client-statement/route outputs except necessary truthful source labels; do not issue false cash-custody acknowledgments.

## C11 — Safety, compatibility and deployment boundaries

Feature defaults disabled/unconfigured; no real wallet is seeded. New schema/endpoint/permission work belongs to later implementation and may be tested only on an explicitly disposable database. Existing code continues unchanged when feature is disabled. Supported old clients cannot spoof new funding metadata; unknown contracts fail closed. New clients negotiate capability/contract version and show unavailable on an older server.

API/repository checks cover actor/device/object/account/context on every mutation and private read. Clients do not pass authoritative holder, verified status, GL posting flag or balance. Keep protected file content checking, size limits, version digests, private storage, audit and restore/retention policy. Extend backup/restore manifest and disaster-recovery tests to new evidence/link tables; no public URLs or logs containing real balances/photos/references. Offline attendance outbox remains separate; financial verification, allocation and balance-changing commands remain online-only with explicit status recovery.

Do not expand API settlement capabilities, connect a wallet with MPIN/OTP, scrape the app, execute actual transfers, rotate signing keys, change package version or auto-run delivery. Pre-registration records are not legal authorization to lend and not a workaround for wallet terms. Actual owner identity/grants, account use, opening count/cutoff, and future legal-book mapping are launch inputs, not fictional test defaults. No live database reset, deletion of actual evidence or automatic company cutover.
