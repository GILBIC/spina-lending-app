# Reviewed owned-wallet transfer accounting

Migration 0150 adds explicit accounting for independently verified source and destination legs of an owned-wallet transfer. Operational transfer recording does not create a journal. Management must review current evidence and confirm the retained preparation before posting each leg.

The source leg debits 1040 Transfer Funds in Transit for the actual principal, debits 5240 Bank Charges Expense for a separately recorded positive source fee, and credits the source wallet's explicitly mapped cash account for their sum. The destination leg debits its own mapped cash account and credits 1040 for the actual principal. Each leg uses the Manila calendar date of its own verified event. A source-only transfer can correctly retain a positive 1040 balance across a reporting cutoff; destination evidence dated after the cutoff cannot clear that earlier balance.

Both accounts must belong to the configured book and the same Treasury context. Both current immutable wallet mappings are pinned. Current Management journal authority and explicit private access to both wallets are required for review, preparation, retrieval, posting and retries. No real book identity, wallet mapping, balance or transfer amount is seeded. Only the deterministic 1040 chart control is added, with conflicting existing definitions rejected.

Admission requires the exact original account-transfer event, matching principal and optional source-fee movement lines, retained recipient evidence, no event revisions, no receipt/source-link reuse and exactly one transfer use. The destination requires an exact retained source posting with a date no later than its own. Metadata, reservations, payout/refund events, source-unconfirmed destination accounting, revised events and reversed chronology do not qualify.

Preparations retain full private admission snapshots, their digest, mapping identities, the actor and a confirmation token. The public API exposes approved identity/date/amount/fee fields and journal coordinates, excluding raw evidence and mapping snapshots. Posting revalidates source and authority in the transaction that posts through the existing journal engine and creates the immutable audit. Exact retries return the same journal. Generic posting, cancellation or reversal cannot replace this audit; a protected correction adapter remains required.

Later actual operational evidence remains appendable. Adding the missing destination does not alter an earlier source snapshot: source history excludes the mutable transfer version and the future destination-event pointer. Changes to the source event, transfer identity/amount or chart accounting meaning retain the original money proof while flagging correction review. Retiring or renaming a chart account preserves historical coverage.

The status view exposes one proof per actual leg. The transfer reconciliation compares native principal in transit with the retained journals at the requested cutoff, separately for each transfer. The public close inventory clears only an exact, uncorrected event leg; corrected proofs and unregistered 1040 activity remain blockers. Overall source coverage remains explicitly partial.

The router factory is `create_treasury_transfer_accounting_router`. Under the existing web and mobile financial-accounting Treasury prefixes it provides transfer review/prepare and transfer-preparation read/post endpoints. The caller supplies the transfer, leg, both mapping identities, digest, request identity and explicit confirmation; it never supplies journal amounts or chart codes.
